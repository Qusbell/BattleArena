# 구현 상태 — 확정 필요 사항과 알려진 한계

지시서의 "확정 필요 사항"별로 현재 구현과 제안하는 연결안을 정리했습니다. **확인함**은 실제 경기 기록으로 확인한 것, **미확인**은 코드로만 그렇게 만들었거나 아직 겪어 보지 못한 것입니다.

## 확정 필요 사항

| 항목 (지시서) | 현재 구현 | 제안 / 비고 |
|---|---|---|
| 강제 종료 경기를 일반 비교에 포함할지 (3-1) | 종료 신호 없이 월드가 닫히면 `MatchEndReason='Forced'`로 기록하고 `participant_result`도 씀. **집계의 비교 조건 뷰(`v_match_condition`)는 `Forced`와 종료 기록이 없는 경기를 제외함** | `weapon_stats`, `weapon_totals`는 경기 단위라 제외하지 않음. 포함하고 싶으면 `v_match_condition`의 `JOIN match_end` 조건을 바꾸면 됨 |
| 경기 종료 직전 피해의 처리 경계 (3-1) | 종료 처리 중이던 피해 이벤트는 끝까지 기록하고, 종료 이후에 새로 시작한 이벤트는 버림 | **미확인**: 코드 설계이며 경계 상황을 일부러 만들어 보지는 않음 |
| 스킬 피해 (5-2) | 스킬 피해 경로가 없어 `DamageSource`는 `Weapon` 또는 `Environment`만 쓰임. 뷰 `v_record_issues`는 `Skill`이 들어오면 오류로 표시 | 스킬을 도입할 때 기록 지점과 식별 방법을 정해야 함 |
| 거리 측정 전에 공격자가 사망·리스폰한 경우 (5-2) | 발사 당시 생애(스폰)와 현재 생애가 같을 때만 `EngagementDistance`를 기록하고, 아니면 NULL | **미확인**(코드상 그렇게 동작). 0으로 채우지 않음 |
| 피해 0인 명중을 이벤트로 남기는지 (5-2) | **남김.** `ApplyDamage`가 0을 돌려줘도 피해 행을 만듦 | 명중률 정의: `HitRate`는 "피해 행이 1개 이상 있는 공격 수 / 발사 수". 0 피해를 빼고 싶다면 `weapon_stats`의 `hits` 조건에 `InputDamage > 0`을 추가 |
| 동시 적용 가능한 버프 구분 (7-2) | 컴포넌트가 하나의 현재 버프만 가지므로 단일 태그로 충분. 새 버프가 이전 것을 대체하면 `Replace` | 여러 버프를 동시에 허용하게 바꾸면 `buff` 테이블에 버프 식별 컬럼이 필요 |
| 기본 무기를 제외한 선호 순위 (9-2) | **구현함.** `character_weapon_stats`는 기본 무기 포함, `character_weapon_stats_no_default`는 기본 무기(스폰 때 항상 지급되는 무기)를 뺀 순위 | 두 뷰는 서로 다른 순위이므로 섞어 쓰지 말 것 |
| 해시·실수 표현·구조체 직렬화 (3-2) | `BotSettingsHash` = 9개 값을 `%.9g`로 이어붙인 문자열의 MD5 앞 16자 + `B` 접두. `SettingsVersion` = 설정 JSON 전체의 MD5 앞 12자 + `S` 접두. 실수는 SQLite REAL(`%.17g`로 손실 없이 저장), 구조체는 JSON 텍스트 | 같은 해시에 다른 값이 들어오면 DB 트리거가 거부함 |
| 저장 실패 시 재시도·보관, 종료 시 저장 완료 확인 (8-2) | **구현함.** 쓰기는 0.25초 주기로 한 트랜잭션에 모음. 잠금·디스크 같은 일시적 오류는 묶음 전체를 되돌리고 최대 8번 재시도, 계속 실패하면 `<DB>.failed.sql`에 보관. 데이터가 거부된 문장은 재시도하지 않고 오류와 함께 같은 파일에 보관. 종료 시 못 쓴 문장도 보관. 재시도 묶음의 `INSERT`는 `INSERT OR IGNORE`라 이미 저장된 행이 중복되지 않음. 종료 후 최종 저장이 끝나면 `v_record_issues` 오류·외래키 위반·실패한 쓰기 수를 확인해 로그에 남김 | 확인함: 시험 인자 `-ArenaLogSimulateCommitFailures=<n>`(커밋은 됐지만 실패로 인식하는 상황)로 6번 재시도해도 이벤트 중복·누락 없음. **미확인**: 실제 디스크 오류 상황 (UE의 SQLite는 다른 프로세스의 파일 잠금으로는 막히지 않아 그 방법으로는 재현하지 못함) |
| 경기 시계의 0초 (2-4) | **로딩이 끝나 경기 규칙 액터가 경기 시작을 알리는 순간**을 0초로 삼음. 그 전에 일어난 이벤트(스폰 등)는 0초. 규칙 액터가 없는 월드는 첫 스폰이 0초 | 확인함: 샘플 실행에서 스폰이 0초, 첫 발사가 약 2.5초 |
| 환경 피해 (5-2) | 이 게임에는 환경 피해가 없으므로 구현하지 않음. 지시서의 `AttackId`가 NULL인 피해 케이스는 해당 없음 | 사망 원인의 `Environment`는 낙사 등을 위해 코드에 남아 있음 |
| 설정이 참조하는 다른 데이터 자산의 보존 범위 (3-2) | **구현함.** `/Game/QuakeLike_1_0/Data/Item` 아래 DataTable 행과, 그 행이 가리키는 무기 데이터 자산(`DataAsset:PDA_WeaponBase_C`, 무기당 1행, 77개 속성)을 `balance_settings`에 보존. 같은 내용의 해시가 `SettingsVersion`에 반영됨 | 확인함: `DA_RocketLauncher`의 `damage` 50, `explosionRadius` 400, `maxUsageCount` 12가 들어감. 투사체 클래스 안의 값(`BP_RocketLauncherProjectile` 등)과 사운드·이펙트 에셋은 보존하지 않음 |

## 기록하지만 근사치로 채운 값

(`InputDamage`와 장착 사유는 위 표대로 확정되어 근사치가 아닙니다.)

| 항목 | 현재 방식 | 이유 |
|---|---|---|
| `damage.InputDamage` | **정확한 값.** `BPC_Life`의 `OwnerTakeDamage`에서 체력·아머로 나누기 직전의 값(`Get Buff Take Damage`의 Final Damage)을 `Record Damage Input` 노드로 받아 기록 | 확인함: 404건 중 389건은 체력·아머 감소량과 같고, 나머지 15건은 모두 마지막 일격(남은 체력보다 큰 피해). 이 게임은 체력을 0 아래로 내리지 않으므로 `HealthAfter`는 0에서 멈추고, 초과분은 `InputDamage`에만 남음 |
| `damage.HitType` | 무기 데이터의 `explosionRadius`가 0보다 큰 무기만 대상으로, 넘겨받은 피해량이 무기의 직접 명중 피해(`damage`)와 같으면 `Direct`, 다르면 `Explosion`. 폭발 반경이 없는 무기는 항상 `Direct` | 확인함: 로켓 12건 `Direct` / 16건 `Explosion`. **한계**: 직접 명중 피해가 공격 버프 등으로 바뀐 채 들어오면 `Explosion`으로 잘못 분류될 수 있음 |
| `fire.ShotElementCount` | 무기 데이터의 `pellet` 값 (0이면 1) | 확인함: 샷건 16, 나머지 1 |
| `weapon_equip.EquipChangeReason` | 아이템을 줍는 같은 프레임의 교체는 `AutoOnPickup`, 그 외는 `Manual` | 이 게임에는 탄약 소진 시 자동으로 무기를 바꾸는 경로가 없음(`TrySwap`은 탄약 0인 무기로의 교체를 거부할 뿐이고, AI·플레이어 교체는 모두 스스로 고른 교체). 따라서 `AutoOnEmpty`는 발생하지 않으며 이 두 분류가 정확함. 자동 교체를 새로 넣으면 그때 사유를 추가해야 함 |
| `pickup.AppliedAmount` | 체력 아이템은 획득 전후 체력·아머 차이, 탄약은 획득 전후 무기들의 `currentUsageCount` 증가량 합. 무기 아이템은 둘 다 NULL | 확인함: 탄약 제공량 50에 실제 증가량 0, 1, 27, 44가 구분되어 기록됨 |
| `participant.CharacterId` | `SelectedCharacterRow`가 비어 있어 클래스 이름(`BP_AIShooter_C`, `BP_PlayerShooter_C`)이 들어감. `DifficultyId`, `CharacteristicId`는 `Unknown` | 단독 실행에서는 `SelectedCharacterRow`가 비어 있음. 멀티플레이 로비 경로에서는 채워질 수 있으나 **미확인** |
| `spawn.InitialEquippedWeaponId` | 스폰 직후 마지막으로 장착된 무기. 없으면 기본 무기 | 확인함: 샘플 경기 전부 `DA_Pistol` |
| 리스폰 시 `spawn_weapon` | **원인을 고침.** 로드아웃 지급이 이전 생애가 아직 열려 있는 동안 호출되어 이전 생애로 들어가 버렸음. 이제 종료된 생애로 들어온 지급은 다음 생애로 넘겨 기록. 그래도 보고가 없으면 캐릭터가 실제로 가진 무기를 읽어서 기록 | 확인함: 51개 생애 모두 `spawn_weapon`이 있고 모두 2개(`DA_Pistol`, `DA_MachineGun`) |

## 확인한 것 / 못 한 것

확인함 (실제 경기, AI 6 + 플레이어 1, `Lvl_PortalMap`):
- 저장 실패 재시도와 중복 방지(위 시험 인자), 저장 후 검증 로그, 경기 시계 0초 기준
- 한 DB에 여러 경기를 연속으로 쌓고 `MatchId`로 구분해 조회
- `v_record_issues` 문제 없음, 외래키 위반 0건
- 최종 킬/사망 수와 기록에서 센 값이 7명 전원 일치
- 시간 제한 종료(`TimeLimit`)와 강제 종료(`Forced`) 기록
- 아이템 생성·획득·제거 개수 정합 (획득 = `PickedUp` 제거), 사망 드롭은 사망 이벤트에 연결
- 버프 `Gain` / 30초 만료 `Expire` / 사망으로 인한 `Expire`(사망과 같은 시각, 사망 이벤트에 연결)

못 한 것 (**미확인**):
- 지시서 10-1 시나리오 16개 중 아래는 의도적으로 만들어 보지 않음
  - 일부러 이벤트나 상세 기록을 지워서 검증이 잡아내는지
  - 장착 시간 동점과 사용량 0 순위
  - 발사 직후 무기 교체, 발사자가 사망·리스폰한 뒤의 명중 (분석기의 기존 로직으로 발사 당시 스폰 회차를 유지하도록 만들어져 있으나 기록 DB에서는 확인하지 않음)
- 목표 킬 수(`KillTarget`)로 끝나는 경기
- 버프를 겹쳐 받을 때의 `Refresh`와 `Replace`
- 전용 서버 + 클라이언트 환경 (이번 확인은 단독 실행과 에디터 플레이로만 함)
- 장시간(수십 분) 기록 시 DB 크기·성능. 샘플 DB(경기 1개, 집계 뷰 포함)가 약 5.3MB. 300초 경기 1개의 이벤트는 약 5,800개
