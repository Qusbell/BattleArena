# 출발 방향을 이용한 위치 보정 결과

측정일: 2026-10-21. 대상 맵: `Lvl_PortalMap`.

후속 조사: 아래 큰 오차 네 개는 기존 상세 Route가 더 짧은 Link 조합을 놓친 영향이 지배적이었습니다. 배치 변경 후 전체 Link 그래프를 정밀 계산한 결과, 네 추정값의 오차는 -0.38~-1.43%였습니다. 아래 표는 당시 상세 API를 기준으로 한 기록을 보존합니다. [원인 조사](PathLinkOutlierRootCause.md)를 참고하세요.

현재 기본값은 `PathLink.EstimateDirectionStrength=1`, `PathLink.EstimateBlendStrength=0`입니다.
즉 **새 방향 보정만 적용**합니다. 이전 직선거리 혼합 범위는 4000cm로 남아 있지만, 혼합 강도가 0이므로 작동하지 않습니다.

## 보정 알고리즘

출발점과 목표점이 속한 Poly의 중심을 각각 CA, CB라고 하면 기존 추정은 다음과 같습니다.

`기존 추정 = |A-CA| + D(CA,CB) + |B-CB|`

새 방향 보정은 다음과 같습니다.

`보정 추정 = max(|A-B|, D(CA,CB) - dot(A-CA, departure(CA,CB)) - dot(B-CB, departure(CB,CA)))`

- `D(CA,CB)`는 Bake된 중심 사이의 경로 거리입니다.
- `departure(CA,CB)`는 CA에서 CB로 출발할 때의 첫 경로 구간 방향입니다.
- 실제 시작점이 그 방향으로 중심보다 앞서 있으면 거리를 줄이고, 뒤에 있으면 늘립니다.
- 목표점 쪽은 역방향 출발 방향을 이용해 도착 방향을 근사합니다. 역방향이 다른 통로를 선택한다면 실제 도착 방향과 다를 수 있습니다.
- 방향 정보가 없는 쪽은 기존의 양수 중심 오프셋 거리를 유지합니다.
- 방향 보정 강도는 기존 추정과 새 추정 사이를 혼합합니다. 이전 직선거리 보정을 추가로 적용할 수도 있지만, 현재 기본값에서는 껐습니다.
- 도달 불가능한 쌍과 동일 Poly 처리, Link 자체 비용, 정확하게 Bake한 Link 사이 전이 거리는 유지합니다.

추가되는 런타임 작업은 테이블 조회, 압축 방향 벡터 복원·정규화, 내적 계산입니다.
새로운 경로 탐색, NavMesh Raycast, 경로 통과 Poly 복원, 경로점 배열 할당은 하지 않습니다.
이미 Bake된 방향 데이터를 재사용하므로 이 보정 때문에 Bake 경로 탐색이 추가되지도 않습니다.

## 별도의 검증 표본: 새 플레이 가능 200쌍

설정을 선택한 뒤 시드 20261025로 새 표본을 생성했습니다. 미리 정한 기존 방식과 새 기본값만 비교했습니다.
이전 플레이 가능 테스트와 같은 스폰 접근성·바닥·캡슐 공간·양방향 상세 경로 조건을 적용했습니다.
후보 531쌍 중 물리 조건에서 137쌍, 스폰 접근성에서 194쌍이 제외됐습니다.
마지막 양방향 쌍 검사에서 제외된 것은 없으며, 최종 200쌍을 채택했습니다.
예상 거리 조회의 성공 여부는 표본 선정 조건에 넣지 않았습니다.

새 방식의 최대 상대 과대평가는 3.83%, 최대 상대 과소평가는 5.13%입니다.
기존 표본과 새 표본을 합치면 초과는 4/400개(1%)이지만, 기존 표본은 설정 선택에 사용됐다는 차이가 있습니다.
**이번 표본에서는 초과 비율 5% 이하 목표를 충족했으며, 모든 위치나 다른 맵에 대한 보장은 아닙니다.**

### 샘플 31·74·141: 같은 4개 Link를 사용하는 복합 경로

세 정밀 Route는 다음 Link 순서를 공유합니다.

`BP_PathLink12(텔레포트) → BP_PathLink8(낙하) → BP_PathLink27(낙하) → BP_PathLink28(점프 패드)`

Link 사이에는 일반 NavMesh 이동 구간이 있습니다.
시작점은 낮은 위치, 목표점은 높은 위치에 있으며, 직선으로 가깝게 보여도 여러 Link와 일반 이동을 거치는 경우입니다.

| 샘플 ID | 출발 Z(m) | 목표 Z(m) | 첫 Link까지 일반 이동(m) | 마지막 Link 이후 일반 이동(m) |
|---:|---:|---:|---:|---:|
| 31 | 2.23 | 23.73 | 10.572 | 26.508 |
| 74 | 2.23 | 19.10 | 9.650 | 14.345 |
| 141 | 2.42 | 24.73 | 14.649 | 38.225 |

Z는 월드 좌표이며 층 번호가 아닙니다. 세 경로의 Link 사이 공통 부분은 같고, 시작·마지막 일반 이동 구간이 달라집니다.

### 샘플 181: 긴 일반 이동 뒤 낙하 Link 1개를 사용하는 경로

상세 Route는 다음과 같습니다.

`일반 이동 78.166m → BP_PathLink27(낙하) 9.170m → 일반 이동 22.908m`

합계는 110.245m지만, 새 추정은 84.090m여서 약 26.155m 짧게 평가했습니다.
출발 Z는 약 15.60m, 목표 Z는 약 2.23m입니다.

네 정밀 Route 모두 `BP_PathLink27`을 포함합니다. 이는 확인된 공통점이며, 그 Link 자체가 원인이라는 뜻은 아닙니다.
이번 확인은 상세 Route의 구성까지입니다. 추정 그래프가 선택한 Link 순서와 구간별 추정 비용은 아직 대조하지 않았습니다.
후속 대조 실험으로 이 네 사례에서는 상세 API의 후보 제한과 장애물 임시 비용에 따른 경로 선택이 지배적인 원인임을 확인했습니다. 자세한 근거는 [원인 조사](PathLinkOutlierRootCause.md)에 기록했습니다.
따라서 이 4개의 원인을 모두 중심 오프셋이나 부동소수점 오차로 단정하지 않습니다.

좌표는 cm 단위입니다. 아래 값은 표시용 반올림이며, 재현에는 원본 CSV의 전체 정밀도를 사용해야 합니다.

전체 평균은 크게 줄었지만, 기존 표본의 최대 과소평가 차이는 17.09m에서 26.15m로 커졌습니다.
평균 개선과 남은 개별 오차를 함께 고려해야 합니다.

## 검증 및 재현 방법

- 400쌍의 정밀 기준 거리와 상세 Route 전체 필드(구간·PathPoints·Link)가 보정 전후 동일했습니다.
- 예상 거리 조회의 동기 경로 탐색은 모든 측정에서 0회였습니다.
- 1회씩 측정한 네이티브 조회 평균은 수 마이크로초 수준이었습니다. 통제된 지연시간·프레임 Spike 성능 비교로 해석하지 않습니다.
- `BakedRouting` 자동화 테스트가 통과했습니다. 앞·뒤 위치 오프셋, 역방향을 이용한 도착 보정, 직선거리 하한, 방향 누락 시 처리, 직렬화, 기존 혼합·버전 회귀를 포함합니다.
- 에디터 및 Win64 Development 게임 빌드가 통과했습니다.

원래 9가지 설정은 `Scripts/SweepPathLinkPlayableDirection.py`를 Unreal MCP의 `execute_python`으로 실행해 재현합니다.
별도 검증 표본에는 `PATHLINK_DIRECTION_SOURCE`, `PATHLINK_DIRECTION_STEM`, `PATHLINK_DIRECTION_CONFIGS` 전역값을 지정할 수 있습니다.
스크립트는 좌표를 새로 추출하지 않고 원본 CSV를 읽으며, 종료 시 기존 콘솔 변수 값을 복원합니다.

원본 자료:

- 기존 표본: `Saved/PathLinkBench/PlayableDirectionSweep200.csv`, `PlayableDirectionSweep200Summary.json`
- 새 검증 표본: `Saved/PathLinkBench/Lvl_PortalMap_PlayableRoutes200_Seed20261025.csv`, `PlayableDirectionHoldout200.csv`, `PlayableDirectionHoldout200Summary.json`
- 큰 오차 4개의 상세 Route: `Saved/PathLinkBench/DirectionOutlierDetails.json`

이전 방식을 재현하려면 방향 보정 0, 직선 혼합 1, 혼합 범위 4000cm로 설정합니다.
새 기본값은 방향 보정 1, 직선 혼합 0입니다.
버전 2의 방향 Bake가 유효하다면 보정 변수 변경만으로는 재Bake가 필요하지 않습니다.
