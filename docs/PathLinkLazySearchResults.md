# NavPoly 캐시를 활용한 상세 Route 탐색 개선

측정일: 2026-10-21. 맵: Lvl_PortalMap. 사용자가 조정한 Link27 배치를 유지했습니다.

## 구현한 동작

기존 Traversal, Link 자체 비용, 정밀 Link 간 Transition 캐시를 재사용합니다. 시작점과 목표점의 연결 후보는 가까운 6개로 제한하지 않고 전체 Traversal을 포함합니다.

1. 검증된 NavPoly 캐시의 방향 보정 거리를 이용해 첫 검사 경로를 고릅니다.
2. 선택된 시작·끝 연결 구간만 NavMesh로 정밀 검사해 실제 후보 거리를 확보합니다. 직접 걷는 경로도 필요한 경우에만 검사합니다.
3. 미검증 일반 이동 구간을 비용 하한으로 치환한 그래프를 다시 풉니다. 남은 경로가 현재 정밀 경로보다 짧을 가능성이 있을 때만 추가 검사합니다. 캐시 추정값의 과대평가 때문에 후보가 영구 탈락하지 않습니다.
4. 최종 선택된 경로만 출력 Segment와 PathPoints를 생성합니다. 요청 중 이미 조회한 NavPath는 재사용합니다. GetRouteDistance는 동일 경로를 선택하되 출력 PathPoints를 만들지 않습니다.

직선 하한은 투영된 각 일반 이동 구간에만 적용하며 실제 Link 비용을 더합니다. 텔레포트가 있는 전체 경로에 시작→목표 직선거리를 강제로 적용하지 않습니다. 네이티브 Off-Mesh Link·Context 조건 때문에 직선 하한의 안전성을 확인할 수 없으면 일반 이동 하한을 0으로 둡니다.

같은 기본 NavMesh·필터이며 네이티브 Off-Mesh Link가 없고 Bake 서명이 일치할 때, 서로 다른 Island 사이의 일반 이동은 연결되지 않는다는 정적 정보를 사용해 조회를 생략합니다. 같은 Island라는 이유로 도달 가능하다고 단정하지 않습니다. 거리표의 -1도 그 자체로 상세 탐색의 도달 불가 판정에 사용하지 않습니다. 기존 1cm 이내 0거리 처리도 유지했습니다.

Bake가 없거나 맞지 않는 Context에서는 캐시 우선순위·Island 생략 없이 전체 후보의 지연 정밀 검증으로 동작합니다. 매 반복에서 미검증 간선을 하나 이상 확정하거나 탐색을 끝내므로 임의의 후보 확장 횟수 제한이 필요하지 않습니다. 고유한 동적 연결 구간은 최대 2×Traversal 수+1개이며, 최종 선택된 정적 구간의 경로점 생성에는 별도 NavMesh 조회가 필요할 수 있습니다.

이전 후보 수·Trace 배수·확장 설정은 직렬화 및 Config 호환성을 위해 남겼지만 상세 탐색에는 사용하지 않습니다. 공개 Blueprint 함수와 FPathLinkRouteResult 형식, 실제 이동·물리 처리, Bake 형식은 유지했습니다.

최종 기준은 기존 일반 NavMesh 조회가 반환한 거리와 실제 Link 비용입니다. 여기서 정밀 최단 경로는 그 거리와 정적 Transition으로 구성한 전체 Link 그래프의 최단 경로를 뜻합니다.

## 새로운 시작·목표 200쌍

시드 20261026을 사용했습니다. 이전 시드 20261024·20261025의 표본을 재사용하지 않고 새로 생성했으며, C++ 변경 전에 표본과 변경 전 결과를 고정했습니다. 변경 후에도 같은 200개 좌표를 사용했습니다.

- NavMesh 삼각형의 면적으로 가중한 무작위 좌표입니다.
- 바닥 검사, AI 캡슐 반지름 34cm·반높이 88cm의 공간 검사, 스폰 6개 중 하나에서의 접근성 검사를 적용했습니다.
- 시작→목표 및 목표→시작 상세 경로가 모두 존재해야 채택했습니다. 추정 성공 여부로 표본을 선별하지 않았습니다.
- 499회 시도 중 물리 조건 탈락 117회, 스폰 접근성 탈락 182회, 쌍 도달성 탈락 0회, 최종 200쌍입니다.
- 동일 Poly 1쌍, 같은 Island의 서로 다른 Poly 80쌍, 다른 Island 119쌍입니다.

변경 후 200쌍 모두 상세·추정 조회에 성공했습니다. 독립 전체 정밀 그래프와도 200/200 일치했고 최대 거리 차이는 0cm였습니다. 기존 네 사례를 합치면 204/204 일치입니다. 독립 검증에 사용한 일반 NavMesh 조회는 5,228개였으며, 이는 테스트용 전수 검사 비용으로 런타임 알고리즘의 조회 수가 아닙니다.

| 새 200쌍의 지표 | 변경 전 | 변경 후 |
|---|---:|---:|
| 추정 평균 절대 오차 | 0.663m / 1.000% | 0.479m / 0.792% |
| 추정 상대 절대 오차 P95 | 3.200% | 2.734% |
| 10% 초과 과대평가 | 1개 | 1개 |
| 10% 초과 과소평가 | 2개 | 0개 |
| ±10% 초과 합계 | 3/200 (1.5%) | 1/200 (0.5%) |

| 최대 과소평가 | -15.034% | -6.485% |

남은 10% 초과 사례는 새 표본 42번입니다. 정밀 24.828m, 추정 27.828m로 약 3.000m 과대평가하며 Link를 사용하지 않는 일반 이동 경로입니다. 이번 변경은 추정 공식을 바꾸지 않았으므로 이 근사 오차는 남습니다.

새 표본 중 6쌍에서 상세 거리가 더 짧아졌고 길어진 쌍은 없습니다. 나머지 194쌍은 거리가 같았습니다. 변경 후 Link 사용 경로 131개, 여러 Link 경유 42개, 텔레포트 포함 32개, Reverse Traversal 포함 4개였습니다.

## 조회 비용

각 좌표를 먼저 한 번 실행해 캐시를 준비한 뒤 상세 Route를 3회씩, 총 600회 측정했습니다. 동일한 좌표와 설정의 변경 전후 비교입니다. 에디터에서 측정한 요청 시간이며, 실제 게임 프레임 전체 시간이나 물리 이동 성능 측정은 아닙니다.

| 상세 Route 지표 | 변경 전 | 변경 후 |
|---|---:|---:|
| 평균 요청 시간 | 355.531μs | 59.774μs |
| P95 요청 시간 | 779.301μs | 150.301μs |
| 최대 요청 시간 | 1,206.100μs | 340.700μs |
| 평균 동기 NavMesh 경로 조회 | 10.620회 | 3.745회 |
| 최대 동기 NavMesh 경로 조회 | 27회 | 11회 |
| 평균 후보 평가 시간 | 122.327μs | 7.579μs |
| 평균 그래프 탐색 시간 | 17.320μs | 5.151μs |
| 평균 최종 PathPoints 처리 시간 | 3.243μs | 2.039μs |

평균 요청 시간은 약 83.2%, 동기 경로 조회 수는 약 64.7% 감소했습니다. 시간은 에디터 상태와 CPU 상황에 따라 달라질 수 있으며 조회 수는 이번 표본의 알고리즘 작업량을 보여줍니다. NavMesh 조회 수에는 위치 투영을 포함하지 않습니다.

캐시 추정 API는 동기 경로 조회 0회를 유지했고, 204쌍 모두 추정 거리가 변경 전과 정확히 같습니다. 변경 후 새 200쌍의 추정 평균 요청 시간은 6.626μs입니다. 추정 코드 자체는 바꾸지 않았으므로 변경 전 12.375μs와의 차이를 이번 구현의 성능 개선으로 해석하지 않습니다.

GetRouteDistance의 변경 후 평균은 56.780μs였고 204쌍 모두 상세 TotalDistance와 0.001cm 이내로 일치했습니다. 출력 PathPoints 처리 시간은 모두 0이었습니다. 변경 후 런타임 캐시 계측값은 약 0.511MiB이며, 새 영구 테이블은 추가하지 않았습니다.
